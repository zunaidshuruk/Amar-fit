## ✅ PART W — BACKDATED HISTORICAL ENTRY FOR BLOOD GLUCOSE (complete — 4/4 phases + the race-condition fix, all verified)

Zunaid's request: let the user log Blood Glucose readings for a past date, not just today, so HbA1c and other calculated reports are accurate as-of-today when catching up on missed logging — right now, every manual entry saves under today's date regardless of when the reading was actually taken, so a person catching up on 3 missed days would either lose that history or corrupt today's single row trying to cram it in.

**Scope, decided via `AskUserQuestion` (3 questions, this session):**
1. **Blood Glucose only, for now** — not every manually-logged metric (Blood Pressure, Weight, Sleep, Water, Steps all have the same today-only limitation, but extending this pattern to them is explicitly deferred to a future pass, not built here).
2. **Both entry paths, not one or the other:** a lightweight in-app "Add Historical Entry" screen for logging a single past day, **and** a CSV download/fill-in/re-upload flow for catching up several missed days at once.
3. **CSV, not true `.xlsx`** — Zunaid proposed "let the user download an Excel, fill it in, re-upload it" mid-session; flagged the real tradeoff before assuming: a genuine `.xlsx` file needs a third-party Android library (no official Apache POI Android support — the available forks are less-maintained, with real APK-size and compatibility risk), while a CSV template opens and edits identically in Excel, Google Sheets, or Numbers with zero new dependencies. Zunaid picked CSV — the user experience ("download, fill in Excel, re-upload") is the same either way.
4. **Conflict handling:** if a date being entered (via either path) already has any non-zero glucose reading logged, **skip it rather than overwrite** — protects against a stale or re-uploaded CSV silently clobbering data already logged in-app.

**Architecture confirmed this session — the data layer needs zero changes:** `DailyMetric.date` is already the Room primary key, and `repository.saveMetrics()` / `repository.getMetricsForDate(date)` already accept an arbitrary date string, not just today's. The actual blocker is entirely at the `ShasthoViewModel.kt` layer: all 6 glucose setters (`setBloodGlucoseBeforeBreakfast`/`AfterBreakfast`/`BeforeLunch`/`AfterLunch`/`BeforeDinner`/`AfterDinner`) read `todayMetrics.value` and write via `todayDateString`, hardcoded. **Also found:** `writeGlucoseToHealthConnect`'s `BloodGlucoseRecord` sets `time = Instant.now()` — a backdated entry would currently sync to Health Connect under *today's* timestamp instead of the date actually being logged for, which Phase 1 has to fix too, or every backdated reading would show up on the wrong day in Health Connect even though the app's own Room row is correct.

  **⚠️ CRITICAL BUG FOUND WHILE VERIFYING Phase 4 — pre-existing, not new, and NOT limited to Part W:** all 6 glucose setters (`setBloodGlucoseBeforeBreakfast` etc.) are plain `fun`s that internally do `viewModelScope.launch { ... }` — fire-and-forget. Every place in the app that calls more than one of these setters back-to-back for the *same date* (which is the normal case — a user logging 2+ readings at once) launches multiple concurrent coroutines that each independently read the current `DailyMetric` row *before* any of them writes it back, then each writes its own `.copy()` built from that same stale read. Whichever write commits last silently overwrites the others — every field set by an earlier-committing coroutine is lost. Confirmed this pattern existed in **three places**: (1) the **original "Save Readings" button on `GlucoseLogScreen.kt`** (part of the very first Glucose entry screen, verified back in commit `586271c` in Part E — this had been live in production this whole time), (2) **Phase 2's `GlucoseHistoricalEntryScreen.kt` Save handler**, and (3) **Phase 4's `importGlucoseCsv()`**, the most likely to trigger it since a typical CSV row has 2+ non-blank glucose columns.
