## ✅ PART H — MANUAL PORTION / MACRO ENTRY (complete)

User request: let barcode scan and photo scan results have a manual portion-size adjuster, and give food logging a true manual numeric entry option (distinct from the existing "Manual Entry" button, which is actually free-text AI analysis via `analyzeFoodText`, not manual entry at all).

1. [x] **Barcode scan portion-size adjuster** — verified fixed in commit `fdc71c3`. `portionMultiplier` state (default 1f) added, reset alongside `selectedMealType` at every reset point (scan success, scan error, close, dismiss, post-log). `adjustedCalories`/`adjustedCarbs`/`adjustedProtein`/`adjustedFat` always computed (no-op at 1f for photo scans). New −/+ stepper Row, gated strictly to `scanMode == ScanMode.SCAN_BARCODE && parsedCalories > 0`, 0.25 increments correctly clamped to [0.25, 5.0] with buttons disabling at the bounds rather than silently no-op'ing. MarkdownText headline and the `logScannedFood` call both switched to the adjusted values; name/category/description/mealType arguments untouched. Photo-scan mode confirmed unaffected — stepper UI never renders there, multiplier stays a no-op 1f. Diff checked directly.
2. [x] **Photo scan portion-size adjuster** — verified fixed in commit `fecb429` ("feat: enable calorie logging for all scan modes"). Exactly the minimal 1-line change requested: the stepper's visibility gate went from `scanMode == ScanMode.SCAN_BARCODE && parsedCalories > 0` to just `parsedCalories > 0`, so it now shows for both scan modes using the same composable/state/clamping — no duplication, no new UI. **Same push also deleted `debug.keystore` again** (see the recurring-hazard note at the top of this file) — caught and fixed directly, SHA256-verified identical to the known-good version. Diff on `ScannerScreen.kt` checked directly.
3. [x] **True manual macro entry (no AI)** — verified fixed in commit `21626ea`. Adds a segmented "Describe" / "Enter Values" toggle to the top of the existing Manual Entry dialog in `FoodLogScreen.kt`. "Describe" mode is the original free-text `analyzeFoodText` flow, untouched. "Enter Values" mode adds Food Name*, Calories (kcal)*, and Carbs/Protein/Fat (g) numeric fields (digit-only input filtering, decimal allowed for macros), Save gated on name + a valid non-negative calorie count, and calls `viewModel.logScannedFood(name, category = "Manual", calories, description = name, mealType, carbsG, proteinG, fatG)` directly — confirmed no `analyzeFoodText` call in this branch. All manual-entry state (mode + all 7 fields) resets consistently on Save, Cancel, and dialog dismiss. Diff checked directly — `FoodLogScreen.kt` was the only file touched (confirmed via `git diff --stat`), and `debug.keystore` was untouched this time (checked explicitly given the two prior incidental deletions).
